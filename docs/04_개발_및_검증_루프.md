# 개발 및 검증 루프

> English: [Development and verification loop](en/04_development_and_verification_loop.md)

이 프로젝트는 Graph Engineering 방식으로 진행한다. 여기서 그래프는 화면 그래픽이 아니라, 기능마다 **요구사항 → 설계 → 구현 → 검증 → 리뷰 → 완료** 상태를 연결해 관리하는 방법이다.

## 기본 루프

```text
요구사항 확인
    ↓
영향 범위·파일 분배 설계
    ↓
최소 범위 구현
    ↓
실제 빌드·테스트·기기 검증
    ↓
독립 리뷰
    ├─ 통과 → 완료 기록
    └─ 문제 발견 → 재현 → 원인 분석 → 최소 수정 → 재검증·재리뷰
```

## 기능별 관리 단위

기능 하나는 아래처럼 분리해 관리한다.

| 기능 노드 | 연결할 검증 노드 | 완료 증거 |
|---|---|---|
| 전압·전류 읽기 | Fold8 원시값 확인 | 충전/해제 상태의 Logcat 또는 진단 화면 기록 |
| W 계산 | 단위 계산 테스트 | μA·mV 입력과 예상 W가 일치하는 단위 테스트 |
| 값 안정화 | 흔들림 입력 테스트 | 급격한 순간값이 표시값을 과도하게 흔들지 않음 |
| 지속 알림 | Android 14 이상 실행 확인 | 알림 권한 허용/거부, 충전/해제 시나리오 결과 |
| 자동 모니터링 | 백그라운드·절전 상태 확인 | 충전 연결 후 별도 버튼 없이 갱신된 실제 기기 결과 |
| AOD 알림 | Fold8 AOD 설정별 확인 | 아이콘만 표시/본문 표시 여부를 구분한 사진 또는 기록 |
| 폴드 화면 UI | 접힘·펼침 화면 확인 | 두 화면 폭에서 겹침·잘림 없는 스크린샷 |

## 완료 기준

기능은 아래 항목이 모두 충족될 때만 완료로 기록한다.

- 요구사항과 영향 파일이 문서에 명확히 연결됨
- 빌드, 단위 테스트, 필요 시 기기 테스트를 실제로 수행함
- 실행하지 못한 검증은 `미검증`으로 기록하고 PASS로 처리하지 않음
- 요구사항 충족·회귀 위험·누락을 별도로 리뷰함
- Critical/High 수준 문제는 0개임

## 변경 제한

- 작은 문구·오타 수정은 적절한 확인 후 처리한다.
- 여러 모듈 또는 동작 흐름을 바꾸는 작업은 구현 전에 사용자에게 범위와 계획을 제시하고 승인을 받는다.
- 같은 실패에 대한 추측성 수정은 약 5회 이내로 제한한다. 반복 실패하면 증상, 재현 방법, 확인 사실, 시도, 다음 선택지를 정리해 사용자와 논의한다.

## 누적 기록 규칙

각 루프의 중요한 결과는 `docs/03_결정_및_변경기록.md`에 추가한다. 최소 기록 항목은 다음과 같다.

- 기능명과 요구사항
- 바뀐 파일
- 수행한 검증과 실제 결과
- 미검증 항목과 이유
- 리뷰 결과 및 발견된 문제
- 다음 단계 또는 보류 결정
