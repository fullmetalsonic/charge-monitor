# 구조 및 파일 분배

> English: [Architecture and file layout](en/02_architecture_and_file_layout.md)

## 원칙

- 측정, 계산, 서비스 수명주기, 알림 표시, 설정 저장, 화면 표시는 서로 분리한다.
- 화면(Activity 또는 Compose UI)은 직접 배터리 API를 읽거나 알림을 만들지 않는다.
- Android 시스템 API 접근은 `platform` 계층으로 모아, 기기별 예외를 한곳에서 진단할 수 있게 한다.
- 아래 트리는 **향후 생성할 파일 설계**이며, 현재 Kotlin 코드는 아직 만들지 않는다.

## 모듈별 책임

| 영역 | 책임 | 포함하지 않는 책임 |
|---|---|---|
| `data/model` | 전압, 전류, W, 충전 상태의 순수 데이터 정의 | Android API 호출 |
| `domain` | 단위 변환, W 계산, 표시값 안정화, 상태 판단, 측정·알림 갱신 주기 | 알림 생성, 화면 렌더링 |
| `platform/battery` | `BatteryManager`와 배터리 Intent 읽기 | 화면·설정 판단 |
| `platform/notification` | 알림 채널 생성, 대기/충전 알림 구성 | 측정 주기 결정 |
| `platform/system` | 충전 연결·해제, 부팅 등 시스템 이벤트 수신 | 서비스 내부의 계산 |
| `service` | 자동 감시 수명주기, 주기 측정, 서비스 시작/중지 | UI 코드 |
| `data/repository` | 서비스·UI가 함께 쓸 측정 상태와 설정 저장 | Android 화면 구성 |
| `ui` | 대시보드, 설정, 진단 정보 표시 | 직접 배터리 API 접근 |
| `ui/design` | 색상 토큰, 배터리·번개 아이콘, 공통 테마 | 충전 전력 계산 |
| `util` | 단위/시간/문구 형식화처럼 작은 공통 기능 | 비즈니스 정책 |

## 데이터 흐름

```text
Android BatteryManager / 배터리 상태 Intent
        ↓
AndroidBatteryDataSource
        ↓
ObserveChargingState → CalculateChargingPower → StabilizePowerReading
        ↓
ChargeMonitorRepository
        ├─ ChargeMonitoringService → ChargeNotificationFactory → 상태바/AOD 알림
        └─ DashboardViewModel / DiagnosticViewModel → 앱 화면
```

## 자동 모니터링 설계 경계

- 사용자가 자동 모니터링을 켜면 `MonitoringServiceController`가 서비스 시작 조건을 관리한다.
- 충전 이벤트 수신기는 서비스가 이미 준비된 상태에서 빠른 상태 갱신을 돕는다.
- 충전 이벤트만으로 백그라운드에서 장기 서비스를 새로 시작하는 방식은 Android 버전 제한 때문에 주된 신뢰성 수단으로 삼지 않는다.
- 부팅 후 재개 기능은 배포 방식·Android 버전·Fold8 실측 결과를 확인한 뒤 별도 결정한다.
- 서비스 유형과 매니페스트 권한은 구현 직전에 최신 Android 요구사항을 확인하여 결정한다. 현 단계에서 임의의 서비스 유형을 고정하지 않는다.

## 테스트 파일 분배 원칙

```text
app/src/test/.../
├─ domain/CalculateChargingPowerTest.kt
├─ domain/StabilizePowerReadingTest.kt
└─ util/PowerFormatterTest.kt

app/src/androidTest/.../
├─ platform/battery/AndroidBatteryDataSourceTest.kt
├─ platform/notification/ChargeNotificationTest.kt
└─ service/ChargeMonitoringServiceTest.kt
```

단위 계산과 값 안정화는 일반 JVM 테스트로 검증한다. BatteryManager, 알림, AOD 관련 결과는 Fold8 실제 기기 검증이 필요하다.

## Graph Engineering 적용

작업은 기능을 한 번에 완성했다고 가정하지 않는다. 각 기능을 요구사항, 설계, 구현, 검증, 리뷰 상태로 연결하고 다음 단계로 넘어갈 때 증거를 남긴다. 세부 흐름과 기록 형식은 `docs/04_개발_및_검증_루프.md`에서 관리한다.
